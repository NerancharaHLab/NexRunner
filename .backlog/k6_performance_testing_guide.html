🚀 Grafana k6 Performance Testing Guide

คู่มือและแหล่งทรัพยากรฉบับสมบูรณ์สำหรับการเขียนสคริปต์ และบริหารจัดการ Performance Test ด้วย Grafana k6 (รองรับสเกล 400 Concurrent VUs)

⚡ Tool: Grafana k6
🔷 Language: TypeScript / JavaScript
🎯 Protocol: GraphQL / REST HTTP/2

1. สถาปัตยกรรมและมโนทัศน์หลักของ Grafana k6

Virtual Users (VUs) vs Iterations: VUs คือ Thread/Goroutine ที่จำลองผู้ใช้งานจริง 1 คนทำงานพร้อมกัน ส่วน Iteration คือรอบการทำงานของฟังก์ชันหลัก default function()

Executor Name วัตถุประสงค์การใช้งาน เหมาะสำหรับ Test Type
ramping-vus ปรับเพิ่ม/ลดจำนวน VUs ตามช่วงเวลา (Stage) Load Test, Stress Test, Shift Profile
per-vu-iterations กำหนดจำนวนรอบการทำงานคงที่ต่อ VU Smoke Test, Validation
constant-vus คงระดับจำนวน VUs นานตามเวลาที่กำหนด Soak Test / Endurance Test

2. คู่มือการเขียนสคริปต์ GraphQL & Scenario

2.1 การสร้าง GraphQL Client (src/clients/patient.client.ts)

import http from 'k6/http';
import { environment } from '../config/environment.ts';

export function searchPatientByHn(hn: string) {
  const url = `${environment.baseUrl}/cortex-api/graphql`;
  const payload = JSON.stringify({
    query: `
      query GetPatientByHn($hn: String!) {
        patient(hn: $hn) { id hn title firstName lastName }
      }
    `,
    variables: { hn },
  });

  const params = {
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${environment.authToken}`,
    },
    tags: { name: 'GraphQL_GetPatientByHn' },
  };

  return http.post(url, payload, params);
}

2.2 การสร้าง Scenario พร้อม Think Time (src/scenarios/reception.scenario.ts)

import { check, sleep } from 'k6';
import { searchPatientByHn } from '../clients/patient.client.ts';

export function receptionScenario() {
  const res = searchPatientByHn('HN12345');
  
  check(res, {
    'status is 200': (r) => r.status === 200,
    'patient data exists': (r) => r.json('data.patient') !== null,
  });

  // Think Time จำลองการอ่านหน้าจอของเจ้าหน้าที่ (3-5 วินาที)
  sleep(Math.random() * 2 + 3);
}

6. วงรอบการทดสอบและปรับแต่งระบบ (Test -> Tuning -> Retest -> เก็บผล)

🔄 กระบวนการวงรอบทดสอบประสิทธิภาพระบบ (Performance Engineering Loop):
1. Test: ยิงทดสอบค่าน้ำหนัก VUs ตามประเภทการทดสอบ และสังเกตพฤติกรรมคอขวด
2. Tuning: วิเคราะห์หาสาเหตุ (Root Cause Analysis) และปรับแต่งระบบ (DB Pool, Indexing, Pod Autoscaling, Caching, Memory Limit)
3. Retest: ยิงทดสอบซ้ำด้วยสคริปต์เดิมเพื่อยืนยันประสิทธิผลการแก้ไข (Before vs After Comparison)
4. เก็บผล: บันทึกสรุปสถิติ p95, p99, Throughput (RPS), HTTP Error Rate และทรัพยากรฮาร์ดแวร์

📊 ตารางเปรียบเทียบการทดสอบแต่ละประเภทและการปรับแต่ง (Test Types & Tuning Lifecycle Matrix)

ประเภทการทดสอบ (Test Type) เป้าหมาย VUs & Duration วัตถุประสงค์ (Core Objective) สิ่งที่ต้องปรับแต่งในขั้นตอน Tuning การสรุปและเก็บผล (Reporting)
1. Load Test 400 VUs (30-60m) ทดสอบการรองรับภาระงานปกติของโรงพยาบาลช่วงพีคเช้า 8 โมง ปรับเพิ่ม DB Connection Pool (max_connections), เพิ่ม Redis Caching สำหรับ GraphQL, ปรับแต่ง Pod RAM/CPU Limits บันทึก p(95) < 2,000ms, Error Rate < 1%, RPS เปรียบเทียบ Before vs After
2. Spike Test 800-1,000 VUs (พุ่งใน 30s) ทดสอบคิวนัดหมายเปิด 8 โมงเช้ากะทันหัน และดูการ Recovery ของระบบ ปรับ Ingress Nginx worker_connections, ตั้งค่า Queue Buffer/Rate Limiting หน้า Kiosk, ปรับ Pod HPA ให้ขยายตัวเร็วขึ้น บันทึกระยะเวลา Recovery (RTO), สถิติ HTTP 502/504 Timeouts, สถิติกราฟ CPU Throttling
3. Stress Test 600-800 VUs (30-45m) อัดภาระงานเกินปกติเพื่อหาจุดคอขวดแรก (First Failure Point) และจุดแตกหัก ย่อย GraphQL N+1 Queries, ปรับ SQL Query Indexing, แก้ไข DB Deadlocks & Lock Timeouts, เพิ่ม Node.js Memory Heap บันทึกขีดจำกัดสูงสุดที่รับได้ (Max Operating Capacity) และชนิดของ Failure เมื่อเกิด Overload
4. Endurance Test (Soak) 250-300 VUs (2-12h) ยิงระดับคงที่ระยะยาวเพื่อตรวจหา Memory Leak และ Resource Exhaustion แก้ไข Memory Leak (Unbound Listeners/Caches), แก้ไข Unclosed DB Connections/Sessions, ตั้งค่า Log Rotation บันทึกกราฟ RAM Trend Line 12 ชั่วโมง ยืนยันว่าไม่มี Memory Leak หรือ OOM Kills
5. Breakpoint Test ไต่ระดับขึ้นเรื่อยๆ จนพัง หาจุดแตกหักสัมบูรณ์ของโครงสร้างพื้นฐานระบบ (Maximum Capacity Limit) ประเมินขีดจำกัดสูงสุดของฮาร์ดแวร์/คลาวด์ เพื่อวางแผนจัดซื้อสเปกเซิร์ฟเวอร์ในอนาคต บันทึกจุดแตกหัก VUs และขีดจำกัดโครงสร้างพื้นฐานระบบ

7. ตัวอย่างการกำหนด Weight และการกระจายสัดส่วน Traffic Mix ใน Grafana k6

⚖️ การถ่วงน้ำหนัก (Scenario Weighting) ใน Grafana k6:
เป็นการกำหนดสัดส่วนภาระงานหรือเปอร์เซ็นต์ผู้ใช้งานจริงตามข้อมูล Excel (เช่น OPD = 38, IPD = 15, Reception = 10, Pharmacy = 7, Lab = 7 ฯลฯ) เพื่อกระจายจากเป้าหมาย 400 Concurrent VUs เข้าสู่แต่ละจุดงานได้อย่างถูกต้อง

รูปแบบที่ 1: การคำนวณ Weight แบ่ง VUs ให้แต่ละ Scenario (Dynamic Allocation)

import type { Options } from 'k6/options';

// 1. รายการ Scenarios พร้อม defaultWeight จากไฟล์ Excel Data.xlsx
export const TRAFFIC_MIX = [
  { key: 'opdRegistration', defaultWeight: 38 }, // 33.63% -> 135 VUs
  { key: 'ipdBedList',       defaultWeight: 15 }, // 13.27% -> 53 VUs
  { key: 'reception',        defaultWeight: 10 }, // 8.85%  -> 35 VUs
  { key: 'report',           defaultWeight: 8  }, // 7.08%  -> 28 VUs
  { key: 'opdPharmacy',      defaultWeight: 7  }, // 6.19%  -> 25 VUs
  { key: 'labWorklist',      defaultWeight: 7  }, // 6.19%  -> 25 VUs
  { key: 'labSpecimen',      defaultWeight: 6  }, // 5.31%  -> 21 VUs
  { key: 'cashierOpd',       defaultWeight: 6  }, // 5.31%  -> 21 VUs
  { key: 'radiologyTask',    defaultWeight: 4  }, // 3.54%  -> 14 VUs
  { key: 'ipdPharmacy',      defaultWeight: 3  }, // 2.65%  -> 11 VUs
  { key: 'cashierIpd',       defaultWeight: 3  }, // 2.65%  -> 11 VUs
] as const;

// 2. ฟังก์ชันคำนวณโควตา VUs สัดส่วนเปอร์เซ็นต์เป็นจำนวนเต็ม (Integer VUs)
export function allocateVus(totalVus: number, scenarios: typeof TRAFFIC_MIX) {
  const totalWeight = scenarios.reduce((sum, s) => sum + s.defaultWeight, 0);
  const result: Record = {};

  scenarios.forEach((s) => {
    // สูตรคำนวณโควตา VUs ตามสัดส่วน Weight: (Weight / TotalWeight) * TotalVUs
    result[s.key] = Math.round((s.defaultWeight / totalWeight) * totalVus);
  });

  return result; // คืนค่า { opdRegistration: 135, ipdBedList: 53, reception: 35, ... } รวม 400 VUs เป๊ะ
}

รูปแบบที่ 2: การใช้ Weighted Random สุ่มสลับแผนกภายใน VU เดียวกัน

import { sleep } from 'k6';
import { opdClinicFlow } from './scenarios/opd-clinic.ts';
import { receptionFlow } from './scenarios/reception.ts';
import { opdPharmacyFlow } from './scenarios/opd-pharmacy.ts';
import { cashierFlow } from './scenarios/cashier.ts';

export default function () {
  // สุ่มตัวเลขเปอร์เซ็นต์ระหว่าง 0 ถึง 100
  const rand = Math.random() * 100;

  if (rand < 33.63) {
    // 33.63% Weight -> ไหลเข้าแผนก OPD Registration (38/113)
    opdClinicFlow();
  } else if (rand < 33.63 + 13.27) {
    // 13.27% Weight -> ไหลเข้าแผนก IPD Bed List (15/113)
    ipdBedListFlow();
  } else if (rand < 33.63 + 13.27 + 8.85) {
    // 8.85% Weight -> ไหลเข้าแผนก Reception (10/113)
    receptionFlow();
  } else if (rand < 33.63 + 13.27 + 8.85 + 6.19) {
    // 6.19% Weight -> ไหลเข้าห้องยา OPD Pharmacy (7/113)
    opdPharmacyFlow();
  } else {
    // 38.06% Weight -> ไหลเข้าแผนกอื่นๆ (Cashier, Lab, Radiology)
    cashierFlow();
  }

  // Think time จำลองการสลับรอบการทำงาน
  sleep(2);
}

📊 ตารางสรุปเปรียบเทียบรูปแบบการทำ Weight ใน k6

รูปแบบการทำ Weight วิธีการทำงาน ข้อดี เหมาะสำหรับ
1. Multi-Scenario VU Allocation คำนวณ VUs ล่วงหน้าให้แต่ละ Scenario ด้วยสูตรสัดส่วน Weight ควบคุมจำนวน VUs/เจ้าหน้าที่ประจำจุดได้เป๊ะ (เช่น OPD 135 VUs, Reception 35 VUs) Load Test โรงพยาบาล, จำลองจำนวนเครื่องจริง
2. In-Scenario Weighted Random ใช้ Math.random() สุ่มเลือกยิง API ตาม % Weight ใน VU เดียวกัน เขียนสคริปต์ง่าย ใช้เพียง 1 Scenario หลัก API Microservice Test, Web Traffic Random Journey
3. Arrival Rate Weighted กำหนด Target Requests/sec (RPS) แยกตาม Scenario Weight ควบคุมจำนวน Request Throughput ไม่ขึ้นกับ Response Time Open Model Throughput Test
